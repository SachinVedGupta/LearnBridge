# Remote companion and adoption feature specifications

These are **planned features**, not implemented capabilities or passing tests. They extend the [shared contracts](CONTRACTS.md), [architecture](ARCHITECTURE.md), [controlled onboarding](ONBOARDING.md) and [verification rules](VERIFICATION.md). Every acceptance ID below is a scenario a coding agent must implement and verify. The existing local dashboard, MCP bridge and public website do not establish remote execution or adoption measurement.

| Feature | Work package and placement | First useful release |
| --- | --- | --- |
| F28 Phone-to-local agent companion | [W24 in the implementation plan](IMPLEMENTATION_PLAN.md); optional M3 extension after full W07 durable review, W11 official execution and W12 useful planning | Authenticated phone requests for scoped study help and reviewed local tasks while the laptop is awake |
| F29 Website/local setup adoption measurement | [W23 in the implementation plan](IMPLEMENTATION_PLAN.md); public setup/funnel portion early after W05 in M1; optional local activation/activity after W07/W11 in M3 | Public `/setup`, a usable setup prompt, honest visit/copy/account measures; later explicitly opted-in installation reports |

F28 precedes general M6 voice and synchronization. F23/W22 can reuse a verified F28 transport where appropriate, but typed capture, transcription and selected-data sync remain independent optional capabilities with their own gates. F29 does not depend on remote control. Remote relay consent does not opt a student into telemetry.

## F28 — Phone-to-local agent companion

**Meaning and milestone.** M3 optional: a student opens LearnBridge on a phone, selects their paired laptop, asks for a study explanation or Today-plan preview, follows progress and reviews a proposed local task. The official agent runs on that laptop using its own normal account access. The phone is a client, not an additional model subscription, a general remote desktop or a way to bypass the host's approvals. Basic local use remains available without a relay account.

### Feasibility and provider boundary

Official documentation checked October 3, 2026 supports building a custom local Codex client through app-server, including streamed events and approval handling. Use its local stdio interface; TCP WebSocket is explicitly experimental and unsupported. LearnBridge must never publish the app-server, local dashboard or private control socket to the internet. The Codex SDK is another documented way to control local agents, but the selected W11 adapter must prove the conversation/approval lifecycle it needs. [Codex app-server](https://learn.chatgpt.com/docs/app-server), [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk).

Codex's native phone connection and Claude Code's native Remote Control demonstrate official remote workflows. They do not establish a documented third-party LearnBridge website transport. Claude's documented remote flow uses outbound HTTPS to Anthropic and its own web/mobile clients; do not scrape or reverse-engineer that session protocol. Release Codex first if its W11 adapter passes; list Claude remote integration as unsupported until a permitted official adapter and actual workflow are verified. [Codex remote connections](https://learn.chatgpt.com/docs/remote-connections), [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control).

Sign in with ChatGPT also documents an optional authorized plan-usage inference integration in preview. That is a separate F25/W11 mode requiring its own registration, permissions, supported requests and actual inference proof; it does not remotely operate an existing desktop or automatically inherit its login. There is no assumed generic ChatGPT REST endpoint for controlling the student's computer. A separately selected model API mode must disclose its charges and never become a silent fallback after subscription failure. [Plan-usage overview](https://developers.openai.com/siwc/token-sharing-open-source), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

**Proposed route.** Reuse the hosted Next.js/Supabase backend as an authenticated HTTPS relay. A deliberately enabled local companion worker polls outward for bounded jobs, invokes only the reviewed W11 adapter through local stdio, and sends selected status/results back. The website does not open a connection to the laptop. This is a LearnBridge design inference from the documented local interfaces, not an already available provider remote-control API.

### Expected student flow

1. Set up and verify the local workspace and official host first. In the paired local dashboard, enable the optional companion, select the supported host and review exactly which recipes and already selected sources may be used remotely.
2. Sign in to LearnBridge on the phone through its normal verified Supabase account. On the laptop, approve binding that account, this installation instance and this phone session. Use an expiring one-use pairing challenge entered in a form; no credential, pairing secret or approval token goes in a URL, QR URL, clipboard report or chat. A QR may contain a public landing URL and a non-authorizing pending ID only.
3. Review relay processing separately from host-model processing. The first version's relay can read plaintext prompts, selected result text and review payloads protected by HTTPS and account isolation. Show that fact, retention and the selected data before activation. An active relay grant must exist **before the phone transmits a prompt and before any enqueue/store**; missing/expired grants open the consent flow before payload submission. Local source import is permission for neither relay upload nor model processing.
4. On the phone, choose an online bound laptop and one supported recipe. Fetch the current grant/binding status before submitting a bounded request; show its exact destination, source selections, expiry and budget. The relay rechecks authorization before accepting/storing the prompt. On an expiry race, reject/discard the payload without logging or retaining it and preserve the student's draft in the current form. Scope expansion still requires a new source/processing review on the laptop in v1.
5. Show `received`, `leased`, `accepted locally`, running/review/verification events and the final observed outcome separately. Read source-cited study output or a plan preview. Proposed tasks remain in review until the authenticated human accepts their exact payload.
6. Permit remote local-task review only when the laptop explicitly granted that human operation. A phone decision is bound to the exact pending proposal/native approval request, run, account, installation, device, payload hash, current source/record revisions and expiry. Preserve every host approval gate. A host approval that cannot be safely represented or delivered remains **finish on laptop**; it is never auto-approved.
7. Allow Stop and Unpair from either authorized interface. Sleeping/offline laptops cannot execute. Show last-seen time and pending/expired/cancellation/unknown state; do not claim completion from a queued request or wake the computer without a separate supported feature.

### Trust and data contracts

Reuse F27 Run/ActionProposal/ReviewReceipt semantics rather than introducing a second approval engine. Add versioned remote envelopes only when W24 is implemented. UUIDs are opaque identifiers; timestamps are UTC instants; revisions are positive integers. Identity/lease fields are assigned by trusted code, never taken as authorization from model text.

| Proposed record | Minimum fields and invariants |
| --- | --- |
| `RemoteDeviceBinding` | Shared contract fields: server-derived `account_id`, `installation_instance_id`, opaque `workspace_ref`, `device_auth_ref`, allowed recipes, policy revision/processing receipts, state/expiry/revocation. Include the bound phone-session reference and supported destination in the reviewed policy. Binding activates only after account verification and explicit local confirmation. |
| `RelayProcessingGrant` | `id`, owner/binding, allowed request/result/source categories, local source pins or selection fingerprint, destination, retention version, total byte/request/time budgets, expiry, review receipt. Distinct from the existing destination-specific host processing grant. |
| `RemoteJob` | Shared contract fields: binding, server-derived account, recipe/version, bounded `input_ref`/hash, source selection pins, processing grants, `client_request_id`, state/timestamps, lease fields and local run reference. Unique `(binding_id,client_request_id)` binds canonical request bytes. No arbitrary executable, path, tool catalogue, app-server method or model configuration. |
| Lease fields on `RemoteJob` | Monotonic lease epoch, owner worker reference, lease expiry and durable local run/acceptance reference. Atomic claim plus local dispatch ledger; stale epochs cannot publish a verified outcome or begin another execution. No separate second Run database is required. |
| `RemoteEvent` | Shared `id`, job/lease epoch, monotonic sequence, type, bounded permitted payload/reference/hash and receipt time. Unique `(job_id,sequence)`; repeated sequence with different bytes is rejected. No raw host transcript or secrets. |
| `RemoteHumanDecision` | Shared account/phone-session/binding/job/run IDs, immutable proposal/native pending-request ID, exact fingerprint, policy/source/record preconditions, decision and expiry; receipt produced by the authenticated human route. The worker/model has no review-approval principal. |
| `RemoteResultArtifact` | Owner-bound job reference, authenticated content reference, content hash/size/type, selected relay sharing receipt and expiry. First release can use text results; no public bucket or arbitrary local path is exposed. |

Bind **account ↔ installation instance ↔ device**. Do not use a restored workspace's student UUID as proof that it is the originally paired installation. Create a separate installation-instance identity outside transferable backups; restore, reinstall or account change invalidates prior bindings and requires fresh local pairing. Device/relay credentials remain in a supported private local store, excluded from export, backup, Git and logs; the server stores only a credential verifier where applicable. Rotating/revoking them denies subsequent claims and uploads.

The phone holds its normal secure website session, never the laptop's localhost cookies, pairing nonce, `.control`/`.agent` credential, Codex/Claude authentication, browser profile, D2L token or raw app-server stream. Never copy host credentials to Supabase or the phone. Server-side service credentials remain server-side. Relay handlers enforce ownership and role restrictions through verified auth and RLS; a device principal can claim work/report bounded events for its own binding but cannot create human review receipts, grant wider scope or read another device/account.

The first relay is a trusted plaintext service, not a claim that a malicious relay cannot see or alter content. TLS protects transport; it is **not end-to-end encryption**. E2E encryption, key recovery, multi-device sharing and cryptographic approval verification would be a separate reviewed crypto design and release gate. Do not put that claim in the v1 UI. Local policy and official host controls still reject arbitrary commands or expanded scope.

### Delivery, execution and recovery

Delivery state and local F27 Run state are separate:

```text
queued -> leased -> local_accepted -> running
queued/leased -> expired | cancelled | failed
leased -> queued only if the durable dispatch ledger proves no local acceptance
running -> awaiting_student | verifying | interrupted | failed | cancel_requested
verifying -> completed | partial | failed | unknown_outcome
cancel_requested -> cancelled | partial | unknown_outcome
```

The received acknowledgment means the relay saved a `queued` job, `leased` means a worker owns a temporary claim, and `local_accepted` means the laptop durably associated it with a local run before dispatch. `completed` requires the recipe's observed verification predicate. A text delta saying done does not verify a run. Lost acknowledgment, host disconnect or crash after dispatch becomes interrupted/unknown until the local/native thread and action ledger reconcile it. A lease expiry alone must not launch a second agent turn. There is no general exactly-once guarantee for inference charges or external effects without reconciliation. The complete canonical state enum and resumable F27 transitions remain in [CONTRACTS.md](CONTRACTS.md#planned-remote-device-contracts-f28--w24).

Use the versioned starting budgets in [CONTRACTS.md](CONTRACTS.md#planned-remote-device-contracts-f28--w24): request ≤ 16 KiB, context ≤ 48 KiB per read within its cumulative grant, selected result artifact ≤ 2 MiB, one active job per workspace, five-minute registration challenge and 15-minute unstarted job TTL. Proposed additional recipe bounds are three queued requests, prompt ≤ 4,000 characters, ≤ 8 permitted tool calls and ≤ 20 minutes. Store limits as reviewed schema/policy constraints, not model suggestions; a smaller existing tool limit still applies. Start with foreground phone polling and short serverless relay requests; no persistent worker on Vercel is required. Suggested worker polling is 3 seconds during active work and 30 seconds idle with jitter/backoff; heartbeat every 30 seconds, offline after 90 seconds without a heartbeat. Show measured last-seen age, not a guarantee of availability.

The local worker checks binding, recipe, source/host/relay grants, revisions, expiry, lease, budgets and cancellation before every new call **and after every asynchronous read before disclosure or commit**. These checks cover native-turn start, context serialization and result upload separately. Source changes invalidate dependent context/review. Relay result/event delivery also rechecks the phone account, current binding and relay grant before and after asynchronous reads; a revoked grant cannot authorize a cached result. Where delivery depends on local source policy, obtain a fresh local authorization receipt for the exact result/selection; unavailable or unreconciled policy keeps private results withheld, including when the laptop is offline. Do not promise immediate cross-network revocation without this gate. Unpair/revoke denies queued work and future calls; previously transmitted text cannot be recalled. Stop requests persist through network loss; transport shows `cancel_requested` until the laptop acknowledges stopping (the local F27 run may be `cancelling`). Cancellation cannot roll back an already accepted host/provider request, and an uncertain result remains explicit.

Prompt/result relay retention defaults to 24 hours with a visible delete operation and an implemented scheduled purge, as defined in the shared contracts. Retain only necessary, content-free security/delivery metadata for a separately disclosed window. Local run history and backups have their own retention; relay deletion does not erase them or provider/host history. Phone service workers must not cache authenticated content; no private token/content in localStorage, public asset URLs, notifications or error logs. Recheck the server-side auth on every poll, result, review and cancellation route.

### Implementation sequence for W24

1. Complete full W07 durable runs/leases/review and W11 local official adapter gates. The current narrow read/propose bridge is insufficient proof of durable autonomous execution. Pin the supported native protocol and normalize stable thread/turn/approval events; preserve host account, sandbox and approval settings.
2. Define strict F28 envelopes and deterministic state reducers in the shared contract layer. Add fixtures for malformed/replayed messages, source revision changes and unknown native outcomes before enabling network delivery.
3. Add hosted relay tables and narrowly scoped authenticated Next.js routes for pending pairing, binding/revocation, bounded request submission, atomic claim, event upload, result polling, human review and stop. Use transaction/RPC ownership and lease checks; deny direct anonymous table access and service-role browser exposure. Review cloud migrations/configuration before applying them.
4. Add the optional local outbound worker and durable dispatch ledger. Fix the allowed relay origin and official executable through reviewed configuration; accept no model-provided URL/command. Use a bounded environment, private credentials, one writer and verified child shutdown. Setup, doctor and agent-config must not silently enroll or connect a relay.
5. Wire only `study.explain`, `plan.today.preview` and `tasks.propose` initially, using source-cited recipes and current granted context. Use a fresh constrained local host session with only the necessary reviewed tools; do not expose unrelated host projects/history/connectors. Prove actual host restrictions instead of assuming an MCP allowlist sandboxes the entire OS account.
6. Build a responsive phone view for account/device selection, measured availability, reviewed request input, resumable events, source references, proposal review and stop. Render text safely; an approval form retrieves the authoritative exact pending payload and rechecks it at acceptance. Unsupported native approval types pause for laptop review.
7. Implement restore/reinstall/account-change invalidation, credential rotation/revoke, retention purge, offline expiry, conflict recovery and sanitized evidence reporting. Run the deterministic suite, then the actual device/host workflow; update capability and setup docs only for the released modes.

**Live gate.** F28-A12 needs an awake laptop, real mobile browser, actual official host account/plan and real network delivery with permitted usage. Synthetic relay/host fixtures prove protocol/policy behavior only. Repeat expiry, disconnect, stop and one supported approval handoff on each released host/platform. Account login/model catalog/config generation alone is not inference proof. **Non-goals.** Unrestricted remote shell/desktop, automatically reading every app, accessing hidden ChatGPT/Claude sessions, public D2L token upload, silent source expansion, remote application/coursework submission, guaranteed laptop wake, always-on service, generic native-remote REST integration, or E2E protection without a reviewed implementation.

## F29 — Website and local setup adoption measurement

**Meaning and milestone.** Early M1 extension: a visitor understands the hosted versus local choices, opens public `/setup`, successfully copies a versioned setup prompt and can optionally create a LearnBridge account. The owner can see a bounded, privacy-aware adoption funnel. Later M3 extension: a student may explicitly report local activation and meaningful weekly activity. Measure distinct phenomena; visits/copies/accounts/installations are not interchangeable people or proof of product quality.

### Expected public setup experience

`/setup` works without sign-in. Explain prerequisites, current supported OS/host modes, basic local commands, what the setup agent verifies and what still requires the student. Show the exact versioned prompt linking the repository and current setup entry point. **Copy setup prompt** uses the Clipboard API; record success only after its promise resolves. On denial/unavailable clipboard, keep the prompt selectable with clear manual-copy guidance, without counting an unobserved copy. Never embed an owner credential, private path, personal profile or telemetry opt-in in the prompt.

Account creation is optional for local tasks/notes. If offered, state its purpose separately from local installation, relay and marketing. Signing in does not install LearnBridge; copying a prompt does not prove it ran; a page view does not prove a new visitor. Keep service login, analytics and optional local reporting independent.

### Metrics and recommended collection

| Metric label | Exact numerator and limitations |
| --- | --- |
| Page views / visitor estimate | Approved provider's aggregate page-view and visitor-session estimates for public paths/time range. Repeat devices, blockers, bots and provider dedup windows prevent an actual-person count. |
| Successful prompt copies | Accepted, deduplicated `setup_prompt_copy_succeeded` observations emitted after browser clipboard success. A manual copy is unmeasured; optional `setup_prompt_copy_failed` diagnostics do not increment success. Client events can be forged; label observed interaction counts. |
| Setup accounts | Distinct server-verified Supabase account IDs created through the declared setup flow, excluding fixture/admin accounts. Account identity is not an installation or proof of a unique person. |
| Active accounts | Distinct authenticated accounts performing an allowlisted meaningful hosted operation in the measured window, from server success records. Sign-in/page refresh alone is not meaningful activity. Publish the operation definition and edition. |
| Reported local activation enrollments | Distinct explicitly consented enrollment references reporting the versioned local verification predicate once. Self-reported/unaudited; reset/reinstall can create another reference. These are not lifetime-unique installations or people; offline/nonparticipants are absent. |
| Opt-in weekly active installations | Distinct telemetry-only IDs, stable within the specified Monday-to-Monday UTC week, reporting a successful meaningful local action. Rotate at week boundary/reset/reinstall; retries/polling/doctor do not increment it. Multiple devices/resets can represent one person; nonparticipants are absent. |

Conversion ratios between anonymous copies/estimated visitors and verified accounts are **directional aggregate ratios**, not individual funnel attribution. Do not join them without a separately consented attribution design. One person can copy repeatedly or use multiple accounts/installation instances; ad blocking, offline use and opt-out cause undercounts. Visitor counts use the provider's deduplication/session definition; never sum daily visitors and label the result monthly unique people or MAU.

If chosen and approved, use Vercel Web Analytics for public pageviews/visitor estimates, with strict URL redaction. Its documentation describes aggregated visitor identification without third-party cookies, including a temporary visitor hash; it is not proof that the counts equal humans. [Privacy and collected data](https://vercel.com/docs/analytics/privacy-policy).

Vercel custom events require Pro or Enterprise as checked October 3, 2026; Hobby analytics has bounded included events and collection can pause at the limit. Do not promise a free custom-event funnel or silently enable a billed plan. Recommended low-cost route: approved Vercel aggregate pageviews where available plus an independent first-party Next.js/Supabase collector for bounded setup-copy events; existing database free-tier limits still apply. If analytics is not configured, show unavailable metrics and keep setup usable. [Custom events](https://vercel.com/docs/analytics/custom-events), [analytics pricing/limits](https://vercel.com/docs/analytics/limits-and-pricing).

### Proposed schemas and privacy boundary

Strictly allowlist fields; do not accept arbitrary event properties or raw URLs. Anonymous setup analytics must have no email, account ID, persistent visitor ID, prompt/content, filenames, OAuth/query parameters, pairing/session/token or source metadata. Only static public paths such as `/setup` are eligible. Strip query/fragment/referrer values before collection; drop private routes entirely. Operational infrastructure may handle IP addresses for networking/security under its own disclosed policies; do not claim application schema redaction removes all provider infrastructure logs.

| Proposed record | Minimum fields and rules |
| --- | --- |
| `PublicSetupEvent` | `schema_version:1`, random per-event `event_id`, fixed `event_name` limited to `setup_page_view`, `setup_prompt_copy_succeeded`, `setup_prompt_copy_failed`; constant route `/setup`, allowlisted prompt version, server receipt time. Coarse client surface is optional only if explicitly allowlisted. No free-form properties or retained client timestamp. Unique event ID; one event name/payload per ID. |
| `AccountActivity` | Server-verified account ID, `signup_confirmed` or `hosted_meaningful_activity`, UTC day, authoritative successful-operation reference/dedup key and bounded setup attribution. Derive identity through verified Supabase auth; browser-supplied IDs cannot select ownership or forge a successful operation. Private operational table, not anonymous analytics payload. |
| `PrivateAccountDirectory` | Auth-backed account ID, optional provider/user-reviewed display name, verified email when actually confirmed and confirmation state. Available only to authorized admins for the disclosed operational purpose. A display name is not verified legal identity. No name/email exported into analytics; no marketing consent inferred. |
| `LocalTelemetryConsent` | Local-only consent revision, state, schema/purpose/destination/retention versions, reviewed fields, enabled_at/disabled_at. Default `off`; enrollment requires a separate clear human decision. Neither setup/config/doctor nor remote pairing switches it on. |
| Telemetry enrollment metadata | Random telemetry-only weekly installation ID, private enrollment credential verifier and consent/schema version. It is separate from local student/installation authentication and remote binding. A separately disclosed consented activation enrollment reference may deduplicate activation reports; do not reuse it in weekly activity payloads. Optional account association needs a separate explicit choice. Restore/reinstall/reset requires new enrollment. |
| `LocalMeasurementReceipt` | Telemetry-only instance reference, consent version, unique event ID, UTC day/week, release/schema version and fixed milestone `local_setup_completed`, `local_first_agent_workflow_verified` or `local_weekly_active`. No prompt, source, record ID/title, exact path, identity or host credential. Client-reported proof classification remains self_reported. |

Signed-in adoption and anonymous interaction aggregates have separate endpoints/tables; never retroactively join anonymous browsing to an account from shared timestamps/IP/device details. RLS denies public SELECT/UPDATE/DELETE on raw analytics and identity tables. A narrow collector validates and inserts approved anonymous events server-side; public users cannot call a service-role client. Owner/admin reports use a verified server-side role check and aggregate queries, not a hidden route or browser-supplied admin flag. No public user/email directory.

Proposed first-party limits: request ≤ 2,048 UTF-8 bytes; one event per request; ≤ 10 accepted anonymous events per minute per coarse transient abuse bucket, with an independent global storage cap. Use a vetted platform limiter or bounded keyed server-side limiter; any short-lived IP-derived abuse key is never persisted as an analytic visitor identity. Require the expected public origin, strict content type and schema, reject forged/extra properties and log only redacted codes. Origin alone is not anti-bot authentication. Dedupe event ID in a database transaction and reconcile client retry without double counting. Collector failure never blocks copying, account access or local setup.

Raw events/receipts default to 30-day retention and aggregates to 12 months, as defined in [the adoption contracts](CONTRACTS.md#planned-adoption-contracts-f29--w23). Implement deletion/purge and document aggregate anonymization limits before enabling collection. Auth/account/enrollment data follows its separate disclosed lifecycle. Local reporting keeps a bounded unsent queue only while opted in; opt-out purges it immediately, revokes enrollment and prevents further network sends. Historical server deletion follows the disclosed erase operation; already published aggregate counts or external copies are not silently erased by a local toggle.

### State transitions and implementation order for W23

```text
copy: idle -> copying -> copied | failed
event: created_after_observed_success -> queued -> accepted | dropped
local telemetry: off -> reviewed_opt_in -> enrolled -> active -> opted_out
installation: enrolled -> activation_reported -> active_in_window | inactive_in_window
```

Activation is a versioned local predicate: setup/storage healthy, paired synthetic task/note saved and read back after restart. Report `local_first_agent_workflow_verified` separately when an actual selected official host succeeds in the synthetic read/proposal workflow; it is not implied by setup. A local client may report either predicate, but the relay cannot attest it from a boolean. Meaningful activity is successful accepted task/note work or a verified study workflow, not runtime heartbeats, repeated doctor/config calls or unfinished proposals. Emit `local_weekly_active` with a bounded UTC-day receipt after an observed successful action; aggregate distinct telemetry IDs into the defined UTC week. Keep that ID stable inside the week and rotate it at the next boundary; never sum weekly IDs into lifetime-unique installs. Activation deduplication may use a separate explicitly consented enrollment reference. Reinstall/reset can change both; neither establishes unique humans. Rotating IDs alone does not claim cryptographic anonymity/unlinkability. Do not submit user content as activation evidence.

1. **Early M1 after W05:** add public `/setup` and a versioned setup prompt using current instructions, clipboard success/failure UI and a selectable fallback. Optional sign-in remains independent. Link it from the public site/repository only after its content matches current capabilities.
2. Define F29 event schema, metric labels and collection/retention notice. Review any analytics dependency/service configuration first. Implement a strict first-party collector and aggregate owner report using the existing Next.js/Supabase stack, transactional deduplication, bounds, abuse limits and RLS. Enable approved Vercel public pageviews independently; use first-party copy events if the plan lacks custom events.
3. Add server-verified setup account attribution and meaningful hosted operation counters. Keep operational name/email access private and out of analytics; do not add mailing-list enrollment or request unnecessary profile fields. Measure channel/cohort only using approved coarse fields, not full referrers/query strings.
4. Implement a deterministic aggregation fixture with a fixed clock and declared UTC-day/week windows. Show missing collection, excluded bots where known, paused quotas and collector outage as coverage limitations; never substitute click count for installation count.
5. **Later M3 after W07/W11:** add a separate off-by-default local reporting choice, versioned activation predicate, private enrollment credential and bounded content-free queue. Do not add any telemetry enrollment/request to setup, doctor or agent-config. Coalesce retries/activity locally; report only the selected coarse measurements.
6. Implement opt-out queue purge/enrollment revoke, account/installation data deletion, scheduled retention cleanup and an admin authorization audit. Run fixture and actual-browser/live-policy gates, then publish measured labels and methodology with evidence.
