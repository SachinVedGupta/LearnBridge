# Remote companion foundation: disabled, status only

This implements a narrow, opt-in foundation for [F28](../FEATURES_REMOTE_AND_ADOPTION.md#f28--phone-to-local-agent-companion). It is **not a released phone-to-agent product**. Local setup, the dashboard, doctor, agent configuration and backups never activate or enroll it. No provider configuration, migration, deployment or background polling was performed by this implementation.

## What the code actually does

The [shared protocol](../../../web/packages/core/src/remote-companion.mjs) accepts one versioned `study.explain` request with a bounded prompt. It accepts no executable, app-server method, path, provider credentials, model configuration or user-supplied account authority. The request hash is recomputed from its canonical fields by both the API and the relay RPC. A changed retry conflicts; an exact retry keeps one job.

The [local foreground library](../../../web/apps/local-runtime/src/remote-companion.mjs) requires explicit local consent, a current Codex processing grant, selected note revisions, a separately reviewed relay policy and a confirmed account/phone/installation binding. It prepares one source-cited **local study-context note**, records durable acceptance before preparation and reports content-free status. It never invokes an official host, submits a task or uploads selected note bodies/results. `native_execution`, `result_text_delivery`, `remote_task_review` and telemetry remain false. This module has no CLI, dashboard enrollment control, daemon or host adapter wired to it.

The only outward endpoint is the fixed HTTPS LearnBridge relay. Transport forbids redirects and cookie forwarding and has a ten-second timeout. The relay body reader has a five-second deadline and a byte cap; a hanging cancellation callback cannot keep a rejected body read open. There is no inbound laptop listener, public local dashboard, raw app-server transport, shell or credential inheritance.

The [unapplied migration](../../../supabase/migrations/202610030003_remote_companion_foundation.sql) gives anonymous and authenticated roles no direct access to pairing, credential-verifier, prompt or event tables. Narrow RPCs derive account/session authority from verified phone claims or a one-use challenge. Device credentials are hashed on the relay and exist only in local process memory. The private installation marker is outside the workspace/repository; restoring a workspace into another root changes its binding identity. A restart requires fresh pairing. If its old binding is still active, explicitly revoke it or use owner recovery first; otherwise wait for policy expiry. A serialized confirmation check and partial unique index permit only one active bearer binding per installation/workspace. Actual concurrent network workers and in-flight native outcomes still need their separate release verification.

The [phone API](../../../web/apps/web/src/app/api/remote/v1/route.ts) and [device API](../../../web/apps/web/src/app/api/remote/v1/device/route.ts) return disabled before auth/body acquisition unless **both** enable flags are deliberately set. Do not set them merely because tests pass. The implementation is not configured in production.

## Recovery and limits

| Situation | Observed behavior |
| --- | --- |
| Queued request | Acknowledgment means queued, never completed. Unstarted requests expire after 15 minutes. |
| Accepted execution lease expires | Becomes `unknown_outcome`; it is never automatically queued for execution again. |
| Awaiting-student or cancellation control lease expires | A new control epoch preserves the state/run reference. It permits status replay or cancellation acknowledgment, with zero repeated context reads or note preparation. Stale epochs cannot write events. |
| Cancellation arrives after source acquisition | The exact job is fetched again immediately before synchronous local persistence. Cancellation discards the prepared body and is acknowledged without creating a note. An already committed note cannot be recalled. |
| Cancellation is retried | An already pending or acknowledged cancellation returns its existing delivery state without changing it. Pending intent never becomes an acknowledged stop merely because the request was retried. |
| Crash/ambiguous source charge or write | A durable checkpoint becomes unknown immediately, including within the same process. Further polling reconciles status without another selected-body read. A saved note may remain available for local inspection. |
| Laptop/network unavailable | No execution or result text is promised. Offline unpair records `unpair_pending`; only an actual relay response records acknowledgment. Local stop removes in-memory credentials but does not claim relay revocation. |
| Source/host/relay grant changes | New work and context access are denied. Cancellation acknowledgment requires a current processing binding; device revoke remains possible without an unexpired processing grant. Owner recovery or policy expiry prevents future work. |
| A phone session is logged out | This foundation does **not** prove immediate bearer-binding revocation on Supabase logout. A binding can remain valid until explicit revoke or its policy expiry, at most one hour. A fresh verified session can use `revoke_all` to revoke all its account's old bindings and pending challenges without reading their prompts. No different account can do so. A live session-revocation gate is still required before release. |
| Owner deletes a revoked-device prompt | A verified owner, including a fresh session, can erase the prompt from a known owned revoked binding. The delivery tombstone keeps its prior unacknowledged state and local run reference; the response separately reports prompt erasure and whether cancellation was actually acknowledged. An active accepted job still requires stop/revocation first. Private laptop notes and backups are not erased by this operation. |
| Result retrieval | Always withheld. There is no result-text endpoint, cached private result fallback or model/device human-review principal. |

The relay is a trusted **plaintext** service for submitted prompts, protected by HTTPS and owner isolation. It is not end-to-end encrypted. Policy limits are at most three requests, 16 KiB per request and a maximum one-hour consent lifetime; context reads are at most 48 KiB within the existing host grant's cumulative budget. Relay retention is declared as 24 hours. A purge function is implemented, but **no retention scheduler is configured or verified**, so the declared retention cannot be promised in production yet. Relay deletion does not remove private local notes, backups or official host/provider history.

## Objective checks and remaining release gate

Run the [20 protocol/API/SQLite fixtures](../../../web/scripts/remote-companion.test.mjs) and [API fixtures](../../../web/scripts/remote-companion-api.test.mjs) with `node --test scripts/remote-companion*.test.mjs` from `web`. They cover selected/excluded canaries, late revocation/cancellation, exact retry, instance restore, same-process ambiguity, actual SQLite restart, expired control leases, bounded hanging streams, owner recovery/prompt erasure and default-off behavior. API tests exercise the actual Next handlers with synthetic auth/RPC boundaries; they do not prove live Supabase authorization. The [observation queue regressions](../../../web/scripts/adoption-client-regression.test.mjs) additionally verify fresh opt-in after an old aborted send, later opt-out and nonblocking event-ID failure.

The [current 43 SQL assertions](../../../supabase/tests/remote_companion_isolation.sql) passed on October 3, 2026 against disposable PGlite 0.5.8 / PostgreSQL 18.3 with synthetic auth functions and roles. They include direct-RPC scalar/null rejection, JavaScript-compatible UTF-16/Unicode-whitespace bounds, prompt erasure with retained cancellation intent, and one active installation/workspace binding. Combined with student and adoption fixtures, the runner passed 85 SQL assertions plus five JavaScript-to-SQL canonical hash probes. The [exact-hash execution evidence](../../../artifacts/optional-sql-verification.json) matches the current migration/fixture bytes. Disposable SQL checks do not prove deployed Supabase session verification or concurrent sessions. Pairing-cap concurrency must still be measured against the real transactional database.

Before enabling even this status-only foundation, verify deployed Supabase session/owner/RLS behavior, HTTPS delivery, pairing/recovery controls, current source/host grants, mobile sign-in and cancellation, scheduled purge with actual canary deletion, and operational bounds. Before providing the full phone feature, also implement and verify the official native runner, purpose-restricted host permissions, fresh local result-policy receipts, result sharing/deletion, exact human review and the real [F28-A12 gate](../FEATURES_REMOTE_AND_ADOPTION.md#implementation-sequence-for-w24). A queued request, model catalog, local context note or synthetic relay run does not prove a phone answer or completed agent action.
