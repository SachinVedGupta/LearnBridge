# Embedded local Codex execution

LearnBridge's local dashboard can run an actual tutor request using the student's official ChatGPT-managed Codex account. This runs on that student's computer, separately from the hosted API tutor. It is not an API-key fallback, a copied desktop token, or a hosted subscription proxy. Claude remains supported through the external four-tool MCP bridge; embedded Claude execution is not implemented.

## Student flow

1. Install the official Codex CLI **0.154.0**. The adapter checks the exact version, generated stable RPC schemas and a separate experimental thread-start schema for four bounded dynamic functions. A different version is refused until its contract is reviewed.
2. Start and pair the local dashboard. Open **Local AI**, choose **Sign in with ChatGPT**, and follow the official link if sign-in is needed. Finish normal account login yourself. Choose **Check sign-in** afterward.
3. Save a synthetic note first. In **Agent & review**, select that note, choose Codex, and review the expiry and cumulative UTF-8 byte budget. No source is selected by default.
4. Enter a question in **Ask your local Codex host**, select the reviewed grant and confirm the exact request. Your question and approved context reach OpenAI under your account settings and limits.
5. Read the answer, citations and tool receipts. Requested task suggestions remain in the task review queue. Requested document alternatives appear in **Writing**, with the original unchanged. Review and accept/reject their exact content separately.
6. **Stop this request**, grant revocation, browser disconnect, sign-out or a changed selected source withholds further authorized work. Uncertain requests are never replayed automatically. Check review queues for an acknowledged proposal if a later step failed.

The host status distinguishes sign-in from an actual completed model turn. `model_entitlement_verified` becomes true only after a completed request in the current controller session. Normal account rate limits, entitlement failures and unsupported versions remain explicit errors.

## Isolation and authority

The native CLI owns login, refresh and logout inside a separate 0700 LearnBridge profile beside the workspace. LearnBridge validates its own student marker, but never reads `auth.json`, copies an existing Codex profile or writes credentials to its database, backups, Git or HTTP results. Official login URLs exist only in the paired browser/controller, not audit logs. An empty temporary project prevents inherited repository instructions or host skill discovery. Temporary native logs/state are removed when its process closes.

The child uses a sanitized environment, read-only native sandbox, normal approval handling, and fixed disabled shell, apps, plugins, hooks, browser, computer, code-mode, memories and agent features. Effective configuration and the exact four-tool catalogue are checked repeatedly. Unknown active configuration authority is refused. There is no general RPC, executable, model-provider, command or tool setting accepted from HTTP. Requests asking LearnBridge to supply raw ChatGPT auth tokens are rejected, including during catalog lookup before a thread exists; the official managed profile owns authentication.

Each embedded MCP process is bound to **one grant ID**. An ephemeral runtime lease also binds it to the current browser/phone authorizer. For each broker-issued MCP RPC, the lease creates one exact permit bound to the command and canonical argument hash. The authenticated runtime IPC consumes that permit once before any context read or proposal write. A direct native MCP call without the permit, an argument substitution or a second call reusing it is rejected. The broker releases unused permits after the RPC and rechecks current authority after asynchronous work. Leases and permits are neither persisted nor exposed through HTTP; logout invalidates the session before awaiting cleanup. External project MCP registration keeps its existing destination-specific, explicitly selected grant behavior.

## Executed tool and model contract

The default embedded path exposes exactly four eager native dynamic functions: `learnbridge_status`, `learnbridge_context`, `learnbridge_propose_task` and `learnbridge_propose_document`. Their names, argument schemas, bound grant and `deferLoading:false` are fixed by LearnBridge. Native `item/tool/call` requests are handled by the adapter, which serializes calls and issues the corresponding stable `mcpServer/tool/call` RPC through the actual four-tool MCP server and authenticated runtime IPC. These are model-requested calls with actual result hashes; the model's answer cannot invent a successful receipt.

Each turn must successfully call status before context, and context before proposing anything. The broker enforces at most three task proposals, one document proposal and the configured cumulative call budget. Duplicate native requests replay only an identical acknowledged result without another read charge or write. Started items, requests and completed items must agree on call ID, tool name, exact argument fingerprint, success and returned content. Completion that renames a tool, changes arguments or fabricates a result fails closed. The authoritative final answer uses a strict JSON object containing only `answer`; a completed turn without acknowledged status and context receipts is refused.

For every embedded model-requested context call, `max_bytes` is required and fixed to **32000**. The grant's `max_bytes` metadata is a separate cumulative consent budget, not a per-read argument. A model cannot copy a larger grant total into the read or omit the limit: the adapter rejects that request before the context IPC call, without disclosing or charging context. The first call omits ID filters and reads the exact human-selected records; prompt citation IDs must never be guessed as document filters. Therefore the initial selection must fit one read. Task starts preflight the actual projected selection; course/interview studios bound the JSON-encoded exact context note to 24,000 bytes, reserving wrapper space. Narrow a larger selection before starting; later reads can use exact actual IDs returned in the first context result. No read or grant silently expands.

Task-linked agents use `reviewed_proposals`, exposing the four tools above. Ordinary email extraction, Course studio and Interview studio use the trusted internal `read_only` policy and advertise only status/context. The policy is persisted, bound to the request retry hash and enforced before broker delegation and every tool event/request/receipt. Naming a hidden proposal tool in source content or attempting a direct MCP bypass cannot grant permission. HTTP callers cannot choose or broaden this policy. Unsupported legacy read-only execution fails closed rather than falling back to a broader tool set.

Before each proposal write, the adapter and actual MCP/runtime boundary validate exact fields, text bounds, control characters, source membership/revision/hash and the strongest source/request academic policy. Graded sources permit only conceptual outlines and study guides. A model-selected weaker policy cannot override the source. The proposal tools create only pending local records during the turn; a later failed step does not erase an earlier acknowledged proposal. No emails, applications, external files or calendar events are sent or edited.

A separate trusted `structured` mode remains for compatibility and regression tests. In that mode the runtime prepares status/context through stable MCP RPCs, validates all structured suggestions after authoritative model completion, then sends them to the same proposal tools. Its receipts have runtime origin. The dashboard uses model-requested execution; there is no HTTP selector or automatic fallback that silently switches modes.

## Bounded native model selection

Some current native defaults declare `tool_mode: code_mode_only`. At the audited Codex release this hides direct dynamic functions even with `deferLoading:false`, and disabling the code-mode host does not make that model use direct functions. LearnBridge keeps code mode disabled.

For model-requested execution, the adapter rechecks the current official ChatGPT account and requests `model/list` with `includeHidden:false, limit:100` before thread creation. It chooses visible **gpt-5.5**, then **gpt-5.2**, from the release's audited direct-function allowlist. Both were verified against the upstream bundled model catalog at `rust-v0.154.0`, commit `6b9826e3aa83b1a5947db50f4332cb9c65f1b340`. The current RPC does not expose `tool_mode`; the allowlist supplies the audited compatibility decision while the current account catalog supplies availability. Catalog presence is not a completed entitlement check.

A trusted explicit model override must belong to that same allowlist and appear visibly in the current catalog. Missing compatible models, malformed or duplicate catalog records, incomplete pagination, account changes and native replies selecting a different model are rejected before a model turn. There is no model-provider override, arbitrary catalog file or automatic wider tool surface. The selected model must return the expected dynamic-tool sequence in a live check before that account's model execution can be called verified.

Stable and experimental schemas have independent SHA-256 pins. In particular, stable `ThreadStartParams` remains pinned to `792e2f32e37cece971bd616664ea2053741acbed4e9c92e9d1766427718f2ecd`; experimental `ThreadStartParams` is pinned to `25f490368ec6df52a2a3b82a5469d2413307eb93439121b309f415b5648eee7a`. Public schema generation does not read an account, perform a model turn or establish entitlement.

Each call rechecks authority. A dropped acknowledgment has `unknown_outcome`; the controller never silently retries it. Acknowledged proposal receipts survive a later failure while authorized, so the student can inspect the review queue. Revoked context hides retained answer/receipt content from the turn view; it cannot recall material already processed by the host.

The native protocol stream is bounded at 1 MB, including repeated configuration, model-catalog and tool-schema responses. This is distinct from selected-context budgets (32 KB per embedded model-requested or prepared structured-mode read), model answers (16 KB), document drafts (10 KB), tool results (48 KB), event/call counts and request/time bounds. The grant's cumulative context budget still applies to every read. Real combined task/document verification found that the former 256 KB envelope could expire during a configuration recheck before any write; no action was saved by that failed attempt.

## Objective verification

Run the adapter, model-catalog, model-tool, profile, independent proposal-review, host-turn and embedded-MCP suites. They exercise strict real child-process protocol parsing, actual SQLite state, paired HTTP, wrong-grant and stale-lease refusal, direct native MCP bypass, one-use permit replay, completion substitution, tool/call budgets, late logout/check races, invalid later proposals, source edits, cancellation and cleanup. Catalog tests cover preferred/fallback selection, hidden or missing models, malformed/truncated pages, auth-mode changes, raw-token refresh refusal, cancellation/revocation during catalog lookup, schema evidence and selected-model substitution. Synthetic native adapters are explicitly labelled; those tests do not prove account entitlement or model quality.

For a live student check, use one synthetic note and a new short grant. Complete official sign-in and request a source-specific explanation, one pending task and a pending conceptual outline. Verify the selected direct-function model, native status → context → task → document sequence, matching item/request IDs and authoritative turn completion. Read back the model-origin MCP receipts, actual cited answer, zero accepted tasks, the original note's unchanged revision/hash and the unaccepted Writing draft. Restart/pair again and inspect those saved records. Test revocation separately. Never use private course content as an installation fixture.
